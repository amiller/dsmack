# Held-input admission construction

`construct-admission.mjs` captures public prework into one `{pin,stage}` selection per execution. It never reads a returned report or receipt to choose expectations. It reads only root-selected descriptors from protected paths. The root-selected config SHA is mandatory:

```sh
node applications/bounty-settlement/construct-admission.mjs capture /absolute/capture-config.json CONFIG_SHA /absolute/fresh-stage-output
node applications/bounty-settlement/construct-admission.mjs assemble /absolute/assembly-config.json CONFIG_SHA /absolute/fresh-admission-output
```

Use the qualified Node24 runtime and a sanitized environment with no preloaded Node modules. These commands do not launch a VM, import credentials, access replay state, sign, submit a verdict or pay anyone. Output namespaces are exclusive. Retain a refused namespace rather than silently retrying it.

A `dsmack-held-stage-construction/1` config contains exactly `schema`, `stage_id`, `prelaunch`, `request`, `manifest`, `projection`, `checker`, `image_manifest`, `launcher_policy`, `base_admission`, `qualified_base`, `profile`, `inventory`, `enrollment`, `logical_artifacts`, and `suite_selection`. File inputs are exact `{path,bytes,sha256}` descriptors. The input slots and driver command are derived and checked, public commitments are recomputed, and full source delivery is checked as data. The qualified-base descriptor is the original selected source/qualification record; the boot tuple is derived from its held image, command line and base-admission bytes and retained as part of the selection. The single admitted policy image chooses the closed D9 or B44 receipt-producer mode. Baseline outcomes are fixed to failed/1; every other role is completed/0.

For generation and primary review, `suite_selection` is null. For base/candidate it contains descriptors named `generation_selection`, `generation_request`, and `authority`. The latter is a root-selected `dsmack-root-selected-generated-suite/1` public record with exactly `schema`, `stage_id`, `run_id`, `request_sha256`, `suite_sha256`, `generation_selection_sha256`, and `evidence_audit_sha256`. The root creates/selects this record only after the original GEN proof and strict-suite audit pass. It is authorization metadata, not a self-authenticating worker claim. The constructor binds it to the held GEN request, judge, planned run, task, nonce, policy, plan, selection digest and exact suite bytes, and re-runs the unchanged strict suite grammar. The final acceptance operator still authenticates every original GEN proof and checks the suite relationship; this record cannot substitute for those proofs.

Freeze generation selections from held prework first, then authenticate the genuine generated suites, then freeze the corresponding base/candidate selections before those jobs execute. Primary prework can freeze independently. An already completed GEN may be reconstructed from its immutable prelaunch bytes; provenance records the actual later construction time and does not claim that a complete admission existed before that GEN. Do not derive missing selections from outputs or insert fixtures.

A `dsmack-ten-stage-admission-construction/1` config has exactly `schema`, `operator`, `code_root`, `template`, `selections`, `report_keys`, and `operator_config`. `operator` pins the existing reviewed acceptance operator; `template` pins the actual public task/attempt/harness/recipe/delivery template; `selections` contains ten exact descriptors ordered base1..3, candidate1..3, generate1..3, primary-review. The assembler calls that operator's existing `combineAdmission`, then immediately runs the existing `AcceptanceAdapter` constructor over the complete result. Missing stages, duplicate runs/challenges, incorrect base outcomes, wrong image policy or invalid harness closure refuse. The final operator separately reads the actual Store task and submitted attempt transactionally and compares its immutable subject before evaluating/signing; construction itself does not assert the Store is submitted or verified.

`operator_config` contains exactly `schema`, `state_path`, `attempt_id`, `request`, `originals`, `certificate_key_id`, `certificate_public_key`, and `certificate_private_key_path`. It provides all ten genuine original evidence descriptors; the constructor does not open private keys or the Store database. Output is canonical `admission.json`, `operator-config.json`, and a provenance record with every selected input descriptor. Original evidence authentication, full ten-stage acceptance, certificate signing, service acceptance and settlement remain separate operations.
