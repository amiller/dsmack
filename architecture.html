From a task request
to a signed result.

DsmackRunner is a signed command-line app that runs on an Apple silicon Mac. It starts a Linux virtual machine, runs a task inside it, and uses Apple App Attest to sign statements about the software it loaded and the files it got back.

For a browser-test task, the task publisher supplies a container with the browser and test tools, the proposed repository changes, and a command to run. The output includes the test results and any requested screenshots. Someone receiving those files can verify the app’s signatures and compare the recorded software and inputs with the task they requested.

What runs on the Mac?

The macOS app manages a Linux virtual machine, or VM: a separate operating system with its own memory and virtual disks. Inside Linux, Docker starts the task’s container, a package containing the application and its dependencies.

A browser checker and a coding agent can use the same Linux image. Their tools and dependencies arrive in different containers. Changing the tests or repository files therefore does not require rebuilding Linux or the macOS app.

Who supplies the task, and what does the app check?

The task publisher supplies the container, command, input files and rules for accepting the result. On the Mac, an application client prepares these for DsmackRunner. In the current pilot this client is a set of scripts: it checks the release and task signatures, locates the downloaded files, and writes the documents the app will read.

Those documents answer three different questions:

  • Where are the files? The session document gives local paths to the Linux boot files, task disk, temporary disk templates and output location. It also requests a time limit and, where permitted, a private-input disk or network connection.
  • Which exact bytes should they contain? The image manifest lists the Linux kernel, its startup archive and the system disk, with their SHA-256 hashes. A hash is a fingerprint of a file’s bytes. The session records the expected hashes of the task disk and writable-disk templates.
  • Which choices are allowed? The policy document lists acceptable image-manifest hashes and caps memory, CPU count and running time. The pilot’s client derives it from the authenticated release settings.

The client invokes the app with that session, an App Attest key identifier, and a fresh challenge—a value that ties the evidence to this particular request. The Swift code reads the documents, checks the requested image against the policy, and hashes the actual files. A mismatch stops the launch. It copies the checked system and task disks into the run’s working directory and passes the VM configuration to its native backend.

The backend runs Linux until it stops or reaches the deadline, then finishes writing the result disk and console log. Swift checks the backend’s records against the configuration it requested. Only after this finalization does the app produce two signed messages, called App Attest assertions: one signs the launch record; the other signs a result record containing the output-disk and console-log hashes.

The app’s file checks establish that it used the supplied configuration. The recipient’s verifier separately compares that configuration with the software and task it expected. That comparison is what connects an authentic run to the requested work.

What is libkrun, and where does Apple’s hypervisor fit?

libkrun is a virtual-machine monitor library. It provides the machinery for loading Linux, setting up virtual disks and other devices, and managing the VM as it runs. Dsmack includes a modified copy in its native backend, which the Swift app calls through a C interface.

On an Apple silicon Mac, libkrun uses Apple’s Hypervisor.framework. This macOS API lets a process create virtual CPUs and map memory for a guest operating system. Apple’s APIs provide the CPU and memory virtualization; libkrun supplies the virtual machine around them.

Client scripts prepare the task
  → DsmackRunner checks files and configures the run
    → Rust backend + libkrun load Linux and attach virtual disks
      → Hypervisor.framework runs the guest CPUs and memory

The Linux kernel and startup archive come from the image manifest. Files on the Mac appear inside Linux as virtual block devices—disks the guest can read or write. If the task permits networking, the client also starts gvproxy, a helper that carries traffic between the VM’s virtual network device and the host.

The app has Apple’s com.apple.security.hypervisor entitlement, which permits these hypervisor calls. This implementation uses Hypervisor.framework directly through libkrun. Apple’s Virtualization.framework is a separate, higher-level API used by an older implementation in the repository.

Linux starts the container and collects its files

The current base image contains Debian Linux for ARM64, the architecture used by Apple silicon. A supervisor program starts at boot, checks the task package, and asks Docker to run its container. The package describes the command, input files, limits and outputs to collect.

System diskThe reusable Linux installation, mounted read-only
Task diskThe container image, execution settings and public input files
Scratch diskWritable storage for Docker and the task’s temporary files
Result diskThe execution record, captured logs and requested outputs

Keeping these disks separate lets each run start with fresh working storage while using the same system image. Tasks that need credentials use a separate private-input disk and the corresponding client setup. The browser-test preset uses public inputs with networking disabled.

What does the recipient verify?

The returned evidence contains Apple’s attestation of the app key, the two signed assertions, the launch and result records, and the original output files. The verifier already has the task’s expected software hashes, input hashes, challenge and acceptance rules.

It first checks Apple’s certificate chain and the app identity allowed by its policy, then the assertion signatures and replay counters. Next it compares the recorded launch with the expected request and recomputes the hashes of the retained result disk and console log. Inside the disk, it checks the guest’s execution record and exported files.

For the browser example, the final step is to examine the checker’s results against the task’s acceptance rules. A correctly authenticated run can report failing tests. In the bounty application, a passing result must also satisfy the delivery and settlement conditions before payment.

The current execution prototype assumes the Mac’s owner does not tamper with VM storage. Private inputs are staged in plaintext on that host.
