What the signed macOS app actually does

The reference app, DsmackRunner, packages a Swift command-line executable and a native Rust/libkrun backend. The application client invokes the executable inside the app bundle with a session document, a challenge and an App Attest key identifier. This execution path is driven by scripts; it does not require a desktop control panel.

  1. Read and check the selected inputs

    The app reads the session, image manifest and admission policy. It checks the chosen kernel, initramfs, system image and public workload disk against their expected hashes, and stages verified copies for the run. Supported resource and device settings come from the selected policy.

  2. Configure the virtual machine

    Swift calls the native backend through a C interface. The backend configures guest memory, virtual CPUs, boot images and virtual block devices. The session can also select an admitted private-input disk and network connection.

  3. Supervise execution and finalize its files

    The backend runs the VM under the selected deadline, handles termination, and finalizes the result disk and console capture. The app checks the backend’s launch and result records against the admitted session.

  4. Sign and retain the evidence

    Once execution and finalization have completed, the app uses Apple’s DeviceCheck API to produce two App Attest assertions: one over the launch statement, another over the finalized result envelope. It retains the original assertions and the bytes needed to verify them. The launch assertion describes the launch; this path generates both assertions after the run.

Task discovery, GitHub integration, credential preparation, progress displays and bounty settlement live in application clients outside the signed app. The app’s launch code does not hard-code a particular base-image identity; the session and admission policy select it.

How it uses Apple’s virtualization tools

Apple’s Hypervisor.framework exposes hardware-assisted virtual CPUs and guest memory to a macOS process. Dsmack’s native backend uses it through a modified, linked copy of libkrun. The guest is ARM64 Linux running on Apple silicon.

Application client / scripts
  → DsmackRunner: Swift admission and evidence code
    → Native Rust backend + modified libkrun
      → Apple Hypervisor.framework
        → Apple silicon: guest CPUs and memory

libkrun supplies the virtual-machine monitor: loading the guest kernel and initramfs, setting up memory and virtual devices, and handling the guest’s execution and shutdown. Virtual block devices expose the selected disk files to Linux. When networking is enabled, a virtio-net device connects to a separate gvproxy helper prepared by the client.

The signed app requires the com.apple.security.hypervisor entitlement. Apple’s separate Virtualization.framework offers higher-level VM configuration APIs. The current hvf-v3 launch path uses Hypervisor.framework through libkrun; the repository’s older Containerization/Virtualization path is a separate implementation.

App Attest has a different role: it authenticates the app’s key and signed statements. It does not itself boot Linux or measure the guest. Those input and result bindings are implemented by the signed app and its backend.

What the Linux VM contributes

The reusable image boots a read-only, integrity-checked Linux system. Its supervisor validates the workload, starts the selected container with declared inputs and permissions, then exports a receipt and output files. The current reference is dstack-derived Debian ARM64; its Docker runtime, input channels and sandbox policies belong to the image.

Workload disk · read-onlyContainer payload, manifest and public inputs
Scratch disk · writableDisposable container and working state

An optional private-input disk is a separate channel. Network access and private inputs depend on the admitted profile. The packaged alpha accepts selected profiles rather than arbitrary Docker Compose settings.

How a verifier connects the result to the request

The app’s assertions bind the challenge, selected workload and execution records to an App Attest key. The result envelope binds the finalized result disk and console capture. The retained files let an independent verifier recompute those hashes and inspect the guest receipt and outputs.

The verifier checks Apple’s attestation, the admitted app identity, assertion signatures, freshness, expected software and input identities, and the requested workload outcome. The application’s acceptance routine defines success. For bounties, the settlement policy then decides whether the verified result authorizes payment.

The current Mac prototype trusts the host against tampering with VM storage and plaintext private inputs. The VM isolates guest execution, but App Attest does not turn it into a confidential VM protected from the Mac’s owner.
