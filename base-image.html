Architecture

Three layers, with different reasons to change

01 · THE SIGNED MAC APP

Launch + attest

Admit the selected boot and workload inputs, run the ARM64 Linux VM through the native HVF path, retain launch/result evidence, and request App Attest assertions.

The current path lives in runner-vm/. The older runner/ Containerization implementation is a separate historical path.
02 · THE REUSABLE BASE VM

Boot + supervise

Kernel, initrd and a verity-protected, read-only Linux system. The guest supervisor provides container execution, per-run scratch, input plumbing and result export.

The qualified B44 bundle is ARM64, dstack-style Linux plumbing. It is not a macOS guest and it does not identify one particular Claude task.
03 · THE WORKLOAD

Agent, CI, or another program

A validated compose description selects digest-pinned OCI content, commands, declared inputs and the output contract.

Claude Code is one qualified example. Browser CI is another. Supporting an additional harness still needs its own adapter and qualification.
The practical flexibility: changing a task or container within the admitted contract does not inherently require rebuilding or re-signing the Mac app. It does require selecting and admitting the new workload identity.

What actually boots?

AdmitCheck the selected app, base bundle, workload disk and task bindings.
Boot LinuxMount the verified system read-only.
RunUse disposable scratch, the selected workload and permitted input channels.
ExportRetain the result, receipt and output commitments.
Attest + verifyThe Mac app asserts launch and the finalized result; an external checker validates the evidence.

The guest uses separate disks for disposable Docker state, the public workload payload and result export. This separation is why one base can support many task containers. The current packaging still puts OCI content and public task inputs together in a workload disk; that is a delivery choice.

The current compose validator rejects unsupported keys, floating image tags and writable container roots. runsc-hostnet is a specific runtime contract, not a promise of unrestricted Docker host networking.

Where do credentials go?

A separate input channel

A subscription credential is not supposed to be baked into the public workload image. Import is explicit and profile-specific. API-key broker profiles can keep a provider key upstream; broker-file profiles intentionally disclose selected files to their declared audience.

A real limit

The current pilot trusts the host during private-input staging and uses plaintext disk files. Do not promise confidentiality from the Mac’s owner or root. App Attest is not encrypted VM memory.

The core product

“Verified execution” and “task passed” are different answers

QuestionEvidence to check
Did the selected app attest this statement?Apple enrollment/assertions, admitted app identity, expected statement and freshness/replay policy.
Is this the intended execution?Selected base/workload/manifest, task and input commitments, retained receipt and output bytes, and their authenticated relationships.
Did the task succeed?The independently pinned checker, expected outcome and relevant result files. An authentic run can honestly report failure.
Can the worker collect a reward?The accepted task/candidate/payee binding, delivery and escrow state. A proof does not by itself establish payment.

The guest’s compose receipt currently contains attestation: None. The current outer Mac app produces two Apple assertions: one for launch and one binding the finalized run-result envelope. Task semantics remain a downstream check of the retained bytes. Treating the guest JSON alone as an App Attest proof would be a mistake.

A friend should receive an evidence bundle plus a checker invocation and the expected task/release identities. A small signed summary is useful, but cannot replace retained output bytes when the checker needs them. Full VM-result verification is currently Linux-oriented and needs its selected tools and trust inputs; the one-command friend experience is still work to finish.

Repository entry point

Make the first journey small

Inspect before supplying a credential

Read the runner/base/workload boundary, inspect the selected release identity and see exactly which host access and tools the adapter uses.

Run a credential-free diagnostic first

Check prerequisites cheaply, then use a separately qualified small workload. A read-only doctor is not a VM execution test.

Run one pinned task

Use an operator-selected release, task and coordinator. Import a subscription only if that task requires it. Current enrollment and launch are operator-assisted.

Hand another agent the evidence

Include the task identity, verifier/trust inputs, original evidence and output references. Show authentic-success, authentic-failure and invalid-evidence as distinct outcomes.

Actual read-only entry point in the selected source candidate:

node applications/pilot-client/pilot.mjs doctor   --workspace /absolute/private/pilot-state

This command does not launch a VM and its launch-ready verdict stays false. Current execution details belong in docs/pilot/alpha-runtime.md; do not use the older journal interface as a ready-made self-service launcher.

Proposed improvements · not implemented by this report

A stable base should make iteration cheaper

Reuse the large immutable pieces. Deliver the small changing pieces.

Cache verified OCI blobs separately, deliver compact task inputs, and retain full final identity checks. Reuse verified public transfer bases while the current disk format remains in use. A separate content-addressed cache requires an explicit delivery and measurement contract; it cannot be assumed equivalent without checking that boundary.

Use one repeatable run → collect → verify → clean lifecycle. Preserve original evidence, confirm the owned VM/helpers stopped, then retire scratch and staged copies. Add safe aggregate broker timing before changing timeouts again.

These changes would target the repeated packaging, transfer and manual coordination overhead. They are not evidence that a new fast path already exists.

An application on top

Robot workers can participate through a pinned task

The useful unit is a task descriptor: repository/base commit, permitted changes, exact checker, reward rules and evidence/delivery requirements. A worker’s agent can inspect those terms, run the task, then submit the candidate and its execution evidence.

Suggested first integration: take an existing submission such as board search PR #65, freeze its candidate commit and the publisher’s checker, and run one credential-free attested CI check. This proves the selected check ran on that candidate; it does not prove authorship. It avoids requiring another coding-agent development run just to demonstrate acceptance.

Self-claiming requires a verifier and escrow policy that accept that exact task, candidate and payee. A GitHub comment or passing an unrelated test run is not enough. GitHub issues and the website can discover and display tasks; they should not silently invent the success condition after work is submitted. The worker must not be able to substitute its own passing checker for the publisher’s pinned checker.

What the website should expose

Task identity and reward; the pinned success rule; prerequisites and one clear agent entry point; current run state; a downloadable, checkable evidence bundle.
