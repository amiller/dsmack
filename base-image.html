How the base image
runs a task.

The Mac app is the launcher. The Linux base is the reusable execution environment. The task container supplies the program to run.

A task does not need its own Mac application. It selects a compatible container, execution manifest and inputs, which the existing app and VM base can run.

The three layers

Mac · Signed runner app

Admit selected boot/workload inputs · launch through Apple’s hypervisor · retain launch and result assertions

Reusable Linux VM base

Kernel + initrd + verity-protected system disk
Guest supervisor · container runtime · input/output transport

Task container · pinned OCI image

Coding agent, test harness or acceptance routine
Selected command, declared inputs and resource/network profile

Current Mac path: Swift / libkrun / Hypervisor.framework. This is the VM runner, separate from the older Containerization-based node application.

What goes into the VM

Boot bundle

Selected kernel, initrd and protected Linux system image. These supply the reusable base rather than a particular task.

Public workload disk

The pinned OCI image, execution manifest and public task files. The current delivery format packages them together; their identities and bindings are checked.

Private inputs, if used

A separately selected input channel supplies only the data allowed by that profile. The credential-free starter has none.

What happens after launch

  1. Boot the protected system

    The guest verifies and mounts its system image read-only.

  2. Check the workload

    The supervisor validates the selected public payload, manifest and OCI identity before running it.

  3. Run in disposable storage

    The container uses separate scratch space for Docker state and working data. The task runs under the selected limits and network profile.

  4. Export the result

    The guest writes outputs and a receipt to the result disk. The Mac app retains the launch assertion and a result assertion bound to the finalized result envelope.

System disk Read-only Linux base
Workload disk Public program + task inputs
Scratch disk Disposable working state
Result disk Retained outputs + receipt

What the evidence binds

The run has selected identities for the app, base, workload, manifest and task inputs. The guest receipt records workload and output commitments. The app’s App Attest assertions bind its launch and finalized result statements.

The full verifier checks those relationships against independently selected expectations and original retained bytes. It checks both execution validity and the task’s expected outcome. A summary JSON is not a substitute for that evidence.

Apple authenticates the app’s key and assertions; it does not directly measure the Linux VM or judge the code. The runner and verification protocol supply the execution bindings.

What can change independently?

Change What must be selected again New Mac app?
Task or candidate code Task/input identities and acceptance context No, within the supported contract
Agent or test container OCI digest, execution manifest and workload policy No, within the supported contract
Linux kernel or guest runtime Base identity and qualification Not inherently
Native launcher or entitlements App build, signature, identity and qualification Yes

The compose format is a validated subset with digest-pinned images, declared files and bounded resources. It is not unrestricted Docker Compose.

Current implementation and source

The released B44 base and flat starter container have completed actual hardware-backed execution and full result verification on the qualification Mac. Fresh normally secured Mac first-open is not yet qualified. Current private-input staging trusts the Mac’s owner; this is not an encrypted-VM guarantee against host root.
