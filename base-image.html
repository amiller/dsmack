Inside the reusable
Linux base image.

The base image supplies Linux, the guest supervisor and the container runtime. Application code arrives separately in a task container.

The current reference is a dstack-derived Debian trixie ARM64 image. The signed macOS app selects its kernel, initramfs and system image by their recorded identities. This page explains the choices inside that guest; the architecture guide follows the macOS app and Apple’s hypervisor.

Boot and system integrity · Storage · Container policies · Build and versioning

What belongs in the base image?

The base establishes how workloads are admitted, executed and exported. A coding-agent CLI, browser-test harness, repository checkout or bounty’s acceptance routine belongs in the selected container and task inputs. Changing those does not inherently require a new Linux image or a new signed macOS app.

The recipe is a reference selection. A different distribution, kernel or guest runtime would be a new image requiring its own review and qualification. The macOS app can admit a different compatible image without embedding that image into the app.

How the guest boots a checked system

  1. The macOS app selects the boot files

    The image manifest identifies the kernel, initramfs and system-disk bytes. The app checks their hashes and the selected admission policy before using them in the VM.

  2. The initramfs opens the verified system disk

    The boot command line specifies the system device, expected verity root hash and data size. The init script opens a dm-verity mapping with corruption configured to panic, then mounts the squashfs filesystem read-only.

  3. The supervisor takes control

    The init script switches into that filesystem and runs the guest supervisor directly. The supervisor prepares writable disks, validates the workload payload and starts the selected container runner.

dm-verity checks system blocks as Linux reads them. The expected root hash connects those checks to the chosen image identity. This checks guest system integrity; it does not encrypt VM memory or private inputs against the host.

Keep the reusable system separate from each run’s data

vda · SystemRead-only, verity-checked Linux filesystem
vdb · ScratchWritable ext4 disk for ephemeral Docker and working state
vdc · WorkloadRead-only public payload: OCI image, manifest and declared inputs
vdd · ResultWritable ext4 disk for exported files and the receipt

The guest also uses tmpfs for transient runtime files. An optional private-input disk, vde, is admitted separately; private credentials do not belong in the public workload disk. Its contents are not included in the app’s public input measurement.

Each run gets disposable working storage and a result destination. Reusing the same base identity does not mean reusing a previous task’s writable state. Outputs and verification records are preserved before temporary disks are cleaned up.

How the base admits and runs a container

The supervisor validates the public workload archive’s structure before extraction, then checks its payload hashes before execution. The execution manifest selects the OCI image, command, declared inputs, resource bounds and supported security settings. The Compose runner validates this contract before lowering it to Docker Compose configuration.

Container runtime

The implementation supports explicit registrations for runc and gVisor runsc profiles, including a runsc hostnet profile. A requested runtime must be available with the selected runtime closure; the runner refuses an unavailable registration instead of silently falling back. The gVisor selection requires its systrap platform.

Network and sandbox policy

The contract has network-none, NAT and gVisor hostnet modes. Published TCP ports bind to loopback. The guest NAT configuration does not establish a LAN or egress-isolation policy by itself. Which routes a workload can use depends on the selected profile and network setup.

The credential-free browser preset is more specific: network disabled, no credential broker, a read-only container root, nonprivileged execution and pinned seccomp, capability and resource settings. The broader runtime options in the source are not a claim that every combination has been qualified.

A container can bring a coding agent or browser tools without putting them in the base image. Task-specific dependencies, prompts and acceptance checks stay with that workload.

How inputs become checkable outputs

Public input envelopes are bound to the selected manifest and its declared file slots. For profiles using subscription credentials, a separate private-input and broker route supplies the permitted data. The current staging path trusts the Mac’s owner with plaintext private inputs.

After the workload, the guest exporter captures the requested files, records their hashes in an index and receipt, and writes the export-complete marker last. A failed or cancelled workload can also produce evidence; completion of export does not mean the task succeeded.

The macOS app finalizes and hashes the result disk, then binds the result envelope in an App Attest assertion. The independent verifier checks those original bytes against the requested outcome. Follow the complete evidence path →

How the current image is built and versioned

The supported recipe derives an image from an existing pinned base. It checks the selected source lock, parent artifacts, builder and disk templates; overlays the reviewed guest files; then assembles a new verity-protected image and metadata. This is an existing-base derivation, not a clean rebuild of Debian, Linux and every dependency from source.

The current B44 reference is a broker-timeout derivative of the earlier browser-sandbox base. It changes two broker timeout constants, keeps the selected kernel and templates, and produces a new system image, verity root and OS image identity. The broker still buffers responses. That guest-service change does not change the signed macOS app or put a coding-agent CLI into the base.

Changes to the kernel, initramfs, system filesystem or guest services require selecting and qualifying the new base identity. A different task container or task input selects new workload identities while retaining the same base. A native app change requires a new app build and identity.
