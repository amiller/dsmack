Developing
Dsmack.

The repository holds four streams of work that change at different speeds. The platform is what a third party checks, so it is versioned carefully and in public. Apps built on it ship often.

Apps pin the platform release they run on. Workloads belong to the app that uses them and are named by image digest.

Issues and labels

Platform and network issues are filed in the public repository. A label exists to route a decision: which platform area and release (platform:runner, platform:base-image, platform:guest-api, platform:attestation, platform:evidence), which stream (network, app:private-agent, app:bounties, ops), whether it needs a careful review (trust-boundary), and whether it collects on the next minor release (breaking). blocked always comes with what it waits on and a date to check again. Milestones are releases or sprints, such as Platform v0.2.0.

Decisions

Each design decision is a short file in docs/decisions with its status, date and the decision it builds on, so the reasoning behind the current design can be followed back.

Releases

A release starts as an issue from a checklist. A platform release follows releasing: tag, reproducible build, signing, the signed release inventory, notarization and publication with provenance. An app release goes through staging, browser journeys in Chromium and Firefox, a tag, the live testnet deploy, a Mac pool restart and green health checks. The closed issue is the record of the release.
