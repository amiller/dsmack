App Attest for peers

Suppose we want a peer-to-peer network of iPhones and Macs where every node runs the same open-source app, and a node only accepts messages from peers that can prove they run it. The network should be permissionless: anyone can run a node, any developer can build and sign the app, and any peer can check any other without asking a server. Apple's App Attest was built for a different arrangement, but on iOS 27 and macOS 27 it carries enough to do this.

Background

How App Attest is normally used

App Attest (the DCAppAttestService class, iOS 14 and macOS 11 onward) lets an app show a server that a request came from a genuine instance of that app on a genuine Apple device. The app generates a key pair whose private key stays in the Secure Enclave, and asks Apple once to attest it. Apple's answer is a certificate chain to the App Attestation root that binds the key to the app's App ID and to a one-time challenge from the server. After that the app signs requests with the key. Each of these assertions carries a counter, and the server rejects any assertion whose counter has not gone up.

Apple's documentation is written for one reader, the app's own developer. The app can't check itself, because “a compromised app can falsify the results” (Establishing your app's integrity), so the attestation goes to “your server”, which verifies it and later checks assertions “at critical points in the app's life cycle, like when users try to download premium content” (Validating apps that connect to your server). The WWDC21 session motivates it with a modified game client that collects everything without leaving home, and says “Validate on server, not on-device.” The open-source server libraries, devicecheck-appattest (Kotlin) and appattest (Go), implement that server side. Deployed uses we looked at follow the same pattern: Coinbase's CDP wallet backend and World's attestation gateway each verify attestations from their own app, and the Apple evidence goes no further than that backend.

So the developer is trusted twice. The developer runs the only verifier. And the attestation names the app by App ID, a team ID plus a bundle ID, which is a signer identity: whoever controls the team's signing account can ship different code under the same App ID and the attestation looks the same. For a service guarding its own API that is fine, since the developer is the party being protected.

SGX names the two choices. An SGX attestation carries two identities for an enclave, and the verifier picks which to pin. MRENCLAVE is a hash of the code and initial data loaded into the enclave, computed by the CPU as the pages go in. MRSIGNER is a hash of the public key that signed the enclave, so every enclave signed with that key gets the same value. Sealing offers the same pair: data sealed to MRENCLAVE opens only for the identical build, data sealed to MRSIGNER for anything the author signs.

The choice fixes what the developer can do and what they answer for. A verifier that pins MRSIGNER trusts a key. Whoever holds it can change the code at any time and still pass, so the key holder vouches for whatever runs, and the key is what a thief or a subpoena goes after. A verifier that pins MRENCLAVE trusts a build. The developer who produced it cannot swap it, and is not vouching for it either, since anyone with the build can recompute the measurement. Moving to a new build means the verifier admits a new measurement. App Attest's App ID is an MRSIGNER.

In the peer network neither holds. The verifier is every peer, or a contract they all read, and the developer who signed some node's build is one more participant who might cheat. So the attestation has to say which code is running, and peers have to accept builds signed by different developers without keeping a list of whom to trust.

What iOS 27 adds

Starting with iOS 27 and macOS 27, an app can get an MRENCLAVE. Give it the entitlement com.apple.developer.devicecheck.app-attest-opt-in = [CDhash], and the attestation carries the CDHash of the running executable inside the bytes Apple signs. The CDHash is a hash of the CodeDirectory, which is a list of hashes of every 16 KiB page of the executable. So a verifier that pins the CDHash pins the executable's pages, along with the entitlements and Info.plist hashed in the CodeDirectory's special slots.

Apple doesn't document this field. Below is one real attestation, from our probe app on an iPhone running iOS 27.2 beta, pulled apart one layer at a time. Each layer is tied to the next by a SHA-256, and this page recomputes every one of them in your browser.

What the app sends a verifier

attestKey returns a CBOR map with three entries. The certificate chain in x5c runs from a fresh per-key certificate up to Apple App Attestation CA 1. The receipt is for Apple's fraud service. authData is the part we follow down.

Binding 1 · certificate extension 1.2.840.113635.100.8.2 nonce = SHA-256( authData ‖ SHA-256(challenge) )
B
Authenticator data · bytes

authData, with the CDHash inside

The first 164 bytes are standard WebAuthn: a hash of the App ID, flags, a counter, the AAGUID, and the new key. Flag 0xc0 sets the extension-data bit, so a CBOR map of extensions follows. Apple puts the CDHash there as apple_cd_hash_hash_01. Since the nonce above covers all of authData, Apple's certificate signature covers the CDHash.

The CodeDirectory: one hash per page

The CodeDirectory is the blob inside the code signature that everything else hangs off. Apple's TN3126 and codedirectory.h document the layout. After a fixed header come the identifier and team ID, then the special slots (hashes of the entitlements, Info.plist, requirements and resources), then one code slot per 16 KiB page up to codeLimit.

What changes when someone else signs it

We took the executable from plate D and signed it again, with a different identifier (org.example.someone-else) and a new timestamped signature. The new CDHash is , so the attestation from this build would carry a different value. But the signature blob sits after codeLimit, outside the pages. Inside the pages, signing touches only length fields in the Mach-O header on page 0: __LINKEDIT filesize and vmsize, and the LC_CODE_SIGNATURE data size. F
The verifier

Admitting builds from any developer

So a verifier doesn't need to trust any signer, and doesn't need a hand-curated list of CDHashes either. It keeps one approved build. To admit a new CDHash, anyone submits its CodeDirectory and page 0. The verifier checks that code slots 1…n match the approved build, that page 0 matches after zeroing the three length fields, and that the signature flags and entitlements add nothing beyond the approved build's (no get-task-allow = true, no dropped hardened runtime). After that, any attestation carrying this CDHash counts as the approved code. Info.plist is left free: another developer has to change its bundle identifier, so pinning its hash would admit only the original signer.

registerBuild(cd, page0, derEnts):
  require keccak(cd.codeSlots[1..n])       == approvedRestSlots
  require sha256(page0)                     == cd.codeSlots[0]
  require keccak(mask(page0, 3 fields))     == approvedMaskedPage0
  require cd header (flags, execSeg, runtime) == approved
  require sha256(derEnts)                   == cd.specialSlots[-7]
  require entitlement keys and values       == the approved build's, except App ID / team
  rpIdHash[sha256(cd)] = sha256(application-identifier)

We wrote this as a Solidity contract, CDRegistry.sol. Registering a 20 MiB build (1,280 pages) costs about 2.35M gas, once per signed build. Checking an attestation's CDHash after that is a mapping lookup. Every later assertion also carries the CDHash of whatever code is running at that moment, so swapping code under an existing key shows up in the next assertion.

Before iOS 27 · iOS

The same opt-in on iOS 18.5

The same entitlement already does something on iOS 18.5, but the hash lands in the wrong place. It is a fourth top-level entry, cdHash, holding 20 bytes, outside authData and outside anything Apple signs. Anyone between the phone and the server can rewrite it.
