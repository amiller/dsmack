App Attest for
permissionless applications.

Dsmack is a protocol and policy for checking Apple App Attest evidence without making one developer account the system’s trust authority.

Applications choose which code to accept. Independently operated Macs can run approved builds signed under different developer accounts, and peers can check the resulting evidence using shared rules.

The reference implementation provides Solidity verifiers and zero-knowledge proofs for App Attest, plus a Mac runner for executing application workloads.

What is App Attest?

When a remote machine sends you a result, how do you know which app produced it? Apple’s App Attest gives an app a hardware-backed signing key and evidence about the app that can use it.

1 · CREATE A KEY

A key stays on the device

The app creates a key in the Secure Enclave. Its private key stays there; the app asks the system to sign with it.

2 · ATTEST THE KEY

Apple certifies its origin

Apple issues an attestation linking the public key to an app instance on genuine Apple hardware. A verifier checks Apple’s certificate chain and the app identity and code measurements it accepts.

3 · SIGN STATEMENTS

Check later messages locally

The app uses that key to sign hashes of messages, producing assertions. A verifier checks their signatures, the expected message and freshness without asking Apple to certify each message.

Dsmack’s runner uses those messages to identify the requested workload and its returned result. The runner code defines how it observes execution; the task’s acceptance checks define whether the work succeeded.

Apple designed this for an app developer’s server to recognize its own app. Dsmack makes the verification rules available to peers and smart contracts, across accepted builds from different developer accounts.

Choose the accepted code through a shared policy.

Apple’s evidence identifies an app key and the software associated with it. Dsmack separates checking that evidence from deciding which software an application accepts. Its admission policy checks the measured code and app identity, including builds registered under different developer accounts.

This lets a network or smart contract apply common verification rules across operators. App identities remain part of the check; the policy defines which ones qualify.

Direct Solidity verification

Smart contracts check Apple’s certificate chain, enroll the attested app key and verify its signed statements, called assertions.

Zero-knowledge verification

A zero-knowledge proof establishes that the app key’s attestation certificate passed the required checks. A Solidity contract verifies the proof against the application’s policy, then checks subsequent assertions.

Run application workloads on a Mac.

The reference runner is a signed Mac app that starts a Linux virtual machine, runs the chosen workload and signs statements about its launch and result. The app, Linux image and workload can be distributed separately.

Connect the result to the requested work.

1 · SELECT

Specify the work

The request identifies the accepted runner, Linux image, workload and inputs. It includes a fresh challenge to distinguish this run and rules for accepting the result.

2 · EXECUTE

Sign the launch and result

The Mac app creates two assertions. They bind the run’s challenge to statements about the chosen inputs and returned results.

3 · VERIFY

Check the evidence

The verifier checks Apple’s attestation, the app’s signatures, replay protection and the expected identities and file hashes. The application applies its acceptance rules to the result.
