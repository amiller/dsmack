Development bounties
verified with App Attest.

A task creator funds a reward and fixes the acceptance rules. An independent contributor submits code and evidence that the required checks ran on it. A smart contract can validate the claim and pay the contributor.

Dsmack runs the coding agent or acceptance checks in a Linux VM on the contributor’s Mac, and retains App Attest evidence about that execution. The runner is available today. The complete automated claim-and-payment flow below is the intended integration.

What happens on-chain—and what doesn’t.

The repository, task instructions, code and execution stay off-chain. The contract holds funds and applies the settlement rules. This diagram shows the intended automated flow.

1. Define and fund

Off-chain · Creator / GitHub Publish the task

Repository and starting commit, acceptance code, environment, reward terms and delivery requirements.

↓ Creator transaction: funds + terms commitment
On-chain · Smart contract Hold the reward

Record the reward and a hash committing to the task’s settlement terms.

2. Do the work

Off-chain · Worker’s Mac Build and check a candidate

Run the pinned acceptance routine on the candidate. Retain result files and App Attest execution evidence.

No transaction needed while the work runs
On-chain · Smart contract Funds remain in escrow

The contract does not run the coding agent, browser or test suite.

3. Submit and claim

Off-chain · Submission Deliver code and result files

Publish or deliver the candidate and the required artifacts. Evidence binds them to the task and its checker.

↓ Claim transaction: verifiable task / result bindings
On-chain · Smart contract Check the claim and pay

Validate the required evidence, task, payee and unused claim. Release the reward to the bound worker address.

Contract responsibilities shown here are the intended settlement design, not deployed interfaces. Full source and result files stay off-chain; committing their hashes does not guarantee their delivery. The verification path must establish the required execution and acceptance outcome before payment.

What the worker runs

A signed Mac app boots a reusable Linux VM. Inside it, a selected container runs the coding agent or acceptance routine. Separate inputs identify the task and candidate; separate outputs retain the results.

The app produces launch and result assertions. A verifier checks the original evidence against the expected app, base image, workload and task bindings.

What makes a claim valid

App Attest authenticates the app’s key and assertions. The task’s pinned acceptance routine defines success. The contract’s verification rules must bind that passing result to this task and the worker being paid, and reject replay.

Apple does not review the patch or decide whether the bounty is solved. The contract does not trust a contributor’s self-written “passed” file.
