Dsmack protocol draft

A developer should be able to build and sign an approved Mac application under their own Apple developer identity, then send messages that another party can verify. Dsmack combines a policy for recognizing that code with Apple App Attest enrollment and signed assertions.

The contracts already implement these checks. This draft explains their roles and proposes a common specification around them. The exact interoperable message formats and version rules still need to be collected and agreed.

Participants and approved code

The policy owner chooses an approved build. A developer signs a copy under their Apple team. The app creates an App Attest key on its Mac. A recipient decides which policy and signed messages it accepts. Apple certifies the app key; the verifier checks that certification and later signatures.

Signing the same program under another team changes its CDHash, the hash of its signed CodeDirectory. Dsmack's CDRegistry compares a normalized measurement instead: code pages, specified executable headers and entitlements (the app’s declared permissions), with specified signer-dependent fields excluded. The source defines the precise comparison.

The owner calls setBuild to select that measurement. Anyone can call registerBuild with a matching copy's CodeDirectory and required inputs. Registration records its full CDHash and app identity. A new approved build makes registrations under the previous build stop resolving. Developers can therefore share a code policy across signing identities. Worker wallets and payment recipients belong to the application using this mechanism.

Enroll a key, then verify actions

Enrollment checks Apple's evidence before recording a public key. The app creates its key and obtains an attestation containing a leaf certificate and authenticator data. The certificate chain connects that key to an Apple intermediate and the trusted Apple root. The app also supplies clientData, application-chosen bytes whose hash is bound into the attestation.

The existing endorsement registry checks an intermediate against the root once. Enrollment then checks the leaf signature, certificate encoding and validity, app identity, code admission and platform policy. It records the key and expiry, and rejects enrollment of an already enrolled key.

An assertion is a later signature by that key. Its context is the hash of the application data supplied to Apple's generateAssertion. The contract's configured registry calls verify with the expected context and assertion proof. Verification checks the enrolled key, expiry, current code admission and signature, then requires the assertion counter to exceed the last accepted counter.

What a recipient checks

The recipient selects the verifier and approved-code policy it trusts. It determines the expected application data independently, including the action, intended recipient or deployment, and freshness challenge where needed. It then checks the signature against that context and maintains the required replay state. The counter prevents reusing an accepted assertion; application-specific context binds the signature to the intended action.

A successful assertion identifies an enrolled app key running admitted code. The application defines what the signed data means. For example, a VM runner describes its inputs and returned files; a bounty service additionally checks those files against a task's acceptance rules.

Two verification paths, one policy

The direct Solidity path performs the leaf-certificate checks in contract code. The zero-knowledge path proves those checks in a Noir circuit; its adapter verifies the proof and binds 24 public fields to the policy, certificate chain and client data. Both paths verify later assertions with the P-256 precompile.

The App Attest reference explains the checks and recorded measurements. Real Apple captures, Solidity tests and proof-path tests provide starting conformance examples. A shared specification should state precisely which inputs both paths accept or reject.

Execution and bounty profiles

The VM execution profile adds a session document and two assertions: one binds launch evidence; the other binds the finalized result envelope. Current producer formats include dsmack-general-launcher/session/3 and dsmack-general-launcher/v3-run-statement/1. The client and verifier handle retained files and result checking.

The bounty application adds tasks, attempts, delivery and acceptance. The earlier bounty-demo API and current arcade-pilot API are concrete examples. WorkEscrow handles settlement. The current arcade pilot uses an off-chain verifier and a trusted signer bridge to authorize escrow decisions.

What to specify next

Start with the admission core: actors, policy changes, enrollment inputs, assertion encoding and replay rules. Then publish exact byte encodings, domain separators, integer bounds and test vectors for each supported version. The execution profile needs a producer/verifier version map: older verifier constants and newer producer statements coexist today.

Open decisions include how policies identify excluded bundle metadata, how recipients scope challenges, and how independent implementations demonstrate conformance. These are discussion points for the draft; existing contract rules remain available to inspect in the implementation.
